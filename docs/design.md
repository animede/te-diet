# 設計解説: なぜ公式group offloadingより速いのか

[English version](design.en.md)

この文書は、tedietの2つの変換(diet / stream)の設計根拠と、diffusers公式の
`apply_group_offloading` に対して3〜6倍低オーバーヘッドを実現している理由を
説明します。

## 前提となる観察

拡散モデルパイプラインには、テキストエンコーダに関して3つの構造的事実が
あります。

1. **テキストエンコーダは1ジョブに1回しか走りません。** 拡散トランスフォーマ
   (DiT)は6〜50ステップ実行されるのに対し、エンコーダはジョブ先頭の1回だけ
   です。それにもかかわらず全常駐構成ではエンコーダがVRAMを占有し続けます。
2. **パイプラインはエンコーダ出力のうち `hidden_states` しか読みません。**
   `*ForConditionalGeneration` 型のエンコーダをそのまま使うパイプラインは、
   毎回LMヘッド(全語彙への射影)を計算して捨てています。
3. **エンコーダの重みは推論中に変化しません。** したがって重みをホストへ
   「書き戻す」必要は一度もありません。

tedietの全設計はこの3点から導かれます。

## diet: 埋め込みブリッジとLMヘッドスキップ

### 埋め込みテーブルのCPUブリッジ化(`apply_embed_bridge`)

トークン埋め込みテーブル(例: Qwen3-VLは151936×4096 bf16 = 1.16GiB)は、
エンコードの先頭で1回のgatherに使われるだけです。tedietはこのモジュールを
CPUへ移し、`forward` を「input_idsをCPUへ送り、CPUでgatherし、結果を
呼び出し元デバイスへ返す」ブリッジに差し替えます。1024トークンの往復は
数MBであり、転送コストは実測で無視できます。

**なぜ `inputs_embeds` 渡しにしないのか**: パイプライン側で埋め込みを計算して
`inputs_embeds` として渡す素朴な代替案は採用していません。transformersの
マルチモーダルモデルには、特殊トークンの埋め込みベクトルとの比較で
プレースホルダ位置を求める経路(例: `get_placeholder_mask()`)があり、
この経路は埋め込みモジュール本体を参照します。モジュールがCPUにあると
device mismatchで壊れ、さらにマスク導出の分岐自体が本番経路と変わって
しまいます。tedietは**モジュール単位の差し替え**なので、モデル内部の
すべての呼び出し箇所(通常のlookupも特殊トークン比較も)が無変更で
動きます。

### LMヘッドスキップ(`apply_lm_head_skip`)

エンコーダの `forward` を「内側のベースモデルを同一引数で呼び、出力を
そのまま返す」薄いラッパーに差し替えます。`hidden_states` はベースモデルが
生成するので、返る値は完全に同一の経路で作られます。これにより:

- 全トークン×全語彙のlogitsテンソル(1024トークンで約0.3GiB)の一時確保が
  消えます。
- LMヘッドが埋め込みと**非共有**(untied)のモデルでは、ヘッド自体
  (Qwen3-VLで1.16GiB)もCPUへ退避できます。tie判定はパラメータの
  `data_ptr` 比較で自動化しています。tiedのモデルでは埋め込みブリッジが
  ヘッドも一緒にCPUへ移すため、追加の退避は不要です。

## stream: 固定リングバッファ式レイヤーストリーミング

### 方式

デコーダ層(例: Qwen3-VLは36層、bf16計12.9GiB)の全テンソルをpinnedホスト
メモリへ移し、エンコード実行中だけ、コピー専用CUDAストリームが計算の
`window` 層先(既定2)を先読みコピーします。GPU側の受け皿は `window + 1`
個の**固定スロット**で、リング状に使い回します。

同期規約は3行で書けます:

- コピーストリームは `slot_free[slot]`(そのスロットを最後に使った層の計算
  完了イベント)を待ってから上書きします。
- 計算ストリームは `copied[i]`(層iのコピー完了イベント)を待ってから層iを
  実行します。
- スロット数 = window + 1 により、「コピー先スロット」と「現在計算中の層の
  スロット」は常に別物になります。

窓2のとき、PCIe 4.0 x16では層あたりの転送(実測約2.4ms)が層あたりの計算
(同約4.4ms)に完全に隠れます。窓を4や8に広げても速度は変わりません。

### なぜ公式 `apply_group_offloading` より速いのか

同じ「pinned+stream+prefetch」という概念の公式実装に対し、LTX-2.5の
Gemma NF4エンコーダでの実測は次の通りでした。

| 実装 | エンコード時間 |
|---|---|
| 全常駐 | 0.213秒 |
| tediet stream(窓2) | 0.369秒 |
| 公式 group offloading(`use_stream=True`) | 1.25秒 |
| 公式 group offloading(streamなし) | 2.2秒 |

差は3つの設計判断から生まれています。

1. **フックの粒度**: 公式実装は `use_stream=True` のとき
   `num_blocks_per_group=1` が強制され、グループごとの管理フック固定費
   (実測約22ms×48グループ)が支配項になります。tedietは層に直接
   pre/post hookを付け、フック内の仕事をイベント操作とポインタ代入だけに
   絞っています。
2. **復元はポインタ差し替え**: 重みは推論中に変化しないため、層の
   「アンロード」はパラメータの `data` をpinned CPUテンソルへ差し戻すだけで
   済みます。GPU→CPUのコピーは一度も発生しません。
3. **ゼロアロケーション(リングバッファ)**: 公式実装および本実装の旧版は
   層ごとに `.to(device)` で新規確保していました。固定スロットへの
   `copy_(non_blocking=True)` に変えたことで、エンコード中のGPUメモリ確保が
   ゼロになります。

### リングバッファが必要になった実際の事故

旧版(確保式+`record_stream` による遅延解放)は、単体では
expandable_segmentsアロケータの下で問題なく動いていました。しかし
CUDA Graphのメモリプールと同じプロセスに同居させたところ、
expandable_segmentsが効かなくなり、クロスストリームの確保/解放が再利用
されずに**全層分(約14GiB)の予約が積み上がってOOM**しました。固定
リングバッファはアロケータを一切経由しないため、この問題が構造的に
起きません。Graphを使わない構成でも、アロケータ負荷が下がる正しい改善
です。

## 検証の規律: ビット一致

tedietは「速くなったが絵が微妙に変わった」を許容しません。dietもstreamも
計算を一切変えないため、適用前後で隠れ状態は**ビット完全一致**するはず
であり、実際に一致することを適用対象ごとに確認しています。

- Gemma(NF4、LTX-2.5): 一致。2連続実行で復元経路も検証。
- Qwen3-VL(bf16、Qwen-Image 2.1): 一致。同じく2連続実行で検証
  (`tests/test_equivalence_qwen3vl.py`)。

新しいモデルへ適用するときも、まず全常駐で基準出力を取り、適用後に
`torch.equal` で比較することを推奨します。一致しない場合は、そのモデルに
tedietが前提とする構造(下記)が無いことを意味します。

## 新しいモデルへの移植手順

必要なのはモジュールパス3つの特定だけです。

1. `embed_path`: トークン埋め込みモジュール(`nn.Embedding` 相当)。
2. `layers_path`: 構造的に同一な層の `ModuleList`。
3. `inner_path` / `lm_head_path`: `*ForConditionalGeneration` 型なら
   内側ベースモデルとLMヘッド。エンコーダ専用モデル(T5系)なら
   `lm_head_path=None` とし、`apply_lm_head_skip` は不要です。

制約: 全常駐構成専用(accelerate系オフロードと併用不可)、pinnedホスト
RAMを層スタック分消費、同時エンコード不可。層が構造的に同一でない
モデル(異種ブロック混在)ではリングバッファのアサートが失敗します。
